# 備份、還原演練與系統監控維運手冊

> 對應《效能與資安檢測報告》第三級：監控與告警、備份還原演練。2026-11-21 建立。
> 給系統管理員 S 與開發人員使用。畫面在「管理後台 → 開發人員區 → 系統健康檢查與備份驗證」。

## 1. 現況一覽

| 項目 | 現況 |
|---|---|
| 自動備份 | 每天台北時間 02:00（UTC 18:00）自動做一份完整備份，約 20 MB，存在 Supabase Storage 的 `backup-uploads`。內容是 66 張資料表（學生、班級、選課、成績、出缺勤、點名紀錄等）。 |
| 備份**不包含** | 登入帳號（`app_users`）、家長／學生入口帳號（`portal_accounts`）、帳號異動紀錄。還原只適合**同一個** Supabase 專案的災難復原，不能拿備份搬到全新的專案。 |
| 每日健康檢查 | 台北時間 03:00（UTC 19:00，備份之後）自動執行：驗證最新備份、檢查資料庫與儲存空間用量、連線數、備份新舊、資料量有沒有暴跌。結果寫入紀錄，有問題會寄信給系統管理員 S（需設定寄信，見第 3 節）。 |
| 儲存空間 | 免費方案 Storage 上限 1 GB。**沒有清理的話約一個月會滿**：滿了之後備份會失敗，學生照片等上傳也會失敗。本次新增保留規則（見第 4 節）。 |
| Vercel 排程 | 免費方案最多 2 個排程，都已使用（每日備份、每日維護）。健康檢查併在「每日維護」排程裡，沒有另外占用。 |

## 2. 系統健康檢查頁怎麼看

- **立即檢查**：現在就檢查一次（約 2 秒）。
- **驗證最新備份**：把最新一份備份的全部檔案讀回來，確認 (1) 每個檔案都在、能讀；(2) 每張表的列數和備份當時記錄的一致；(3) 學生、教師、班級、選課不是空的；(4) 資料彼此對得起來（選課的學生都存在、成績的選課都存在…）。約 5～30 秒。**這等於「備份能不能用」的自動演練，不會改動任何資料。**
- **清理舊備份**：依第 4 節規則刪除過舊的備份，刪除前會先顯示份數與釋放的空間並要求確認，只有系統管理員 S 本人可以按。
- 狀態燈號：**正常**／**警告**／**嚴重**。判斷標準如下：

| 檢查項目 | 警告 | 嚴重 |
|---|---|---|
| 儲存空間 | 用量 ≥ 70% | ≥ 90% |
| 資料庫大小（免費上限 500 MB） | ≥ 70% | ≥ 90% |
| 資料庫連線數（上限 60） | ≥ 70% | ≥ 90% |
| 資料庫一次簡單查詢 | > 1.5 秒 | > 4 秒，或連不上 |
| 最新備份距今 | > 30 小時 | > 50 小時，或完全沒有備份 |
| 備份驗證 | — | 任何一項不通過 |
| 備份資料量比前一份少 | > 20%（可能有人大量刪除資料） | — |
| 目前資料量比最新備份少 | > 20%（學生、教師、班級、選課、成績任一） | — |
| 有查詢執行超過 60 秒 | 警告 | — |
| 有查詢平均超過 3 秒且已被呼叫 30 次以上 | 警告 | — |

## 3. 怎麼收到告警（兩條路，建議兩條都設）

### 3.1 外部免費監控（最重要：整個網站掛掉時，系統自己通知不了你）

系統提供一個公開的檢查網址：`https://school-sigma-nine.vercel.app/api/health`。正常回傳 200；資料庫連不上或超過 2 天沒有新備份回傳 503。回應只有「正常／有問題」與問題種類，不含任何個資或數字。

用免費服務每 5 分鐘打一次，異常就寄信或推播到你的手機：

1. 到 UptimeRobot（uptimerobot.com）註冊免費帳號（免費方案：50 個監控、每 5 分鐘檢查、信件通知）。
2. Add New Monitor → Monitor Type 選 **HTTP(s)**；URL 填上面的網址；Monitoring Interval 5 分鐘。
3. Alert Contacts 勾選你的信箱（可以多加幾位系統管理員）。
4. 儲存。之後網站掛掉、資料庫連不上、備份超過 2 天沒做，你的信箱都會收到通知。

### 3.2 系統自己寄信（需要設定寄信）

目前正式站**還沒有設定寄信**（沒有 SMTP_HOST 或 RESEND_API_KEY），所以每日檢查發現的問題只會寫進紀錄、顯示在健康檢查頁，不會寄信。要啟用（以 Gmail 為例，免費）：

1. 用一個學校專用的 Gmail 帳號，開啟「兩步驟驗證」，再到 Google 帳號 → 安全性 → 應用程式密碼，建立一組應用程式密碼（16 碼）。
2. Vercel 專案 → Settings → Environment Variables（Production）新增：`SMTP_HOST=smtp.gmail.com`、`SMTP_PORT=465`、`SMTP_USER=<該 Gmail 地址>`、`SMTP_PASS=<應用程式密碼>`、`MAIL_FROM=<該 Gmail 地址>`。
3. 重新部署。設定好之後，系統的通知信（家長申請、審核等）也會一併開始寄送。
4. 寄信規則：只有「問題種類變了」或「同樣的問題超過 7 天」才寄，不會每天重複。

## 4. 備份保留規則（避免儲存空間被塞滿）

以台北時間日期計算，越新越密、越舊越疏：

- 最近 10 天：每一份都留。
- 之後 6 週：每週留最新的一份。
- 再之後 4 個月：每月留最新的一份。
- 最新 3 份一律保留；手動備份至少保留 60 天；路徑格式不認得的備份絕不自動刪除。

依目前 25 份備份試算：會保留 14 份、刪除 11 份（10/27～11/9 之間的），儲存空間從約 495 MB 降到約 280 MB。

**預設只預覽、不自動刪。** 兩種方式真的清理：

- 手動：健康檢查頁按「清理舊備份」（會顯示份數與空間、要你確認）。
- 自動：在 Vercel 環境變數新增 `BACKUP_PRUNE=1`，每日排程會在「最新備份驗證通過、且不超過 36 小時」時自動清理。驗證沒通過或備份太舊時**不會**清理，避免「新的壞了、舊的又被刪掉」。

備份檔含全校個資，不要隨意複製、轉寄。

## 5. 每學期還原演練（約 30 分鐘，建議開學前或放假時做）

目的：確認「真的出事時，備份救得回來，而且大家知道怎麼做」。

**A. 自動驗證（約 1 分鐘）**
1. 健康檢查頁按「驗證最新備份」。
2. 預期：✅ 通過、66 張表、沒有問題。若有「未通過」，先看問題內容（檔案遺失／列數不符／孤兒資料），立刻手動做一次新備份再驗證，仍不通過請聯絡開發人員。

**B. 抽樣比對（約 15 分鐘）**
1. 「備份與還原」區下載最新備份（JSON）。
2. 用文字編輯器或 Excel 打開，隨機挑 3 位學生：核對姓名、班級、選課、近期成績筆數，與系統現在的資料是否一致（備份是前一天凌晨的，當天新增的資料不會在裡面）。
3. 核對最近一次的點名紀錄（備份只存「非出席」紀錄加上點名完成紀錄，兩者合起來才是完整出缺席）。

**C. 還原流程演練（只演練步驟，不要真的按還原）**
把下面第 6 節的檢查表從頭念一遍，確認每個人知道自己負責哪一步、系統管理員 S 的帳號與雙重驗證手機都在。

**D. 異地備份（建議每月一次）**
免費方案沒有異地備份。每月請系統管理員 S 在「備份與還原」按「下載」，存到學校另一台電腦或雲端硬碟（資料夾要限制存取、檔案含全校個資）。

**E. 記錄**
把演練日期、結果、發現的問題記下來。健康檢查頁的「檢查紀錄」會保留最近 90 天的自動檢查結果。

## 6. 災難應變檢查表（資料被誤刪、改壞、或資料庫出問題）

1. **先停手**：通知老師暫停輸入，避免更多資料寫進去。
2. **留存現況**：先在「備份與還原」按「立即備份」做一份手動備份。**還原會整批覆蓋全部資料，而且還原動作本身不會先備份現況**，這一步不能省。
3. **找對的備份**：看備份清單，挑「出事之前最近的一份」；對照各表的列數，確認那份是好的。（健康檢查頁的「驗證最新備份」只驗證最新一份；要用較舊的備份時，請用第 5 節 B 的抽樣方式檢查。）
4. **還原**：只有系統管理員 S 本人可以執行，會要求輸入確認文字。還原會把備份清單裡的**所有**資料表清空再寫回備份的內容。
5. **還原後檢查**：學生人數、班級數、最近的成績與出缺勤、老師能否正常登入。
6. **了解損失**：備份之後到出事之前輸入的資料會消失（最多約一天）。登入帳號、家長／學生入口帳號、帳號異動紀錄不在備份裡，不會被還原也不會被覆蓋。
7. **事後**：記錄原因，必要時請開發人員協助找出誤刪的來源。

## 7. 每學期開學前例行檢查表

- [ ] 健康檢查頁最近 30 次紀錄沒有未處理的「嚴重」。
- [ ] 儲存空間用量在 70% 以下（否則清理舊備份或評估升級方案）。
- [ ] 還原演練 A、B 完成並記錄。
- [ ] 本學期有沒有新增大量資料（例如新學年匯入）：資料庫大小在 70% 以下。
- [ ] 壓力測試：`tools/load-test/db_load_test.py`（需要資料庫連線字串，只在非上課時間跑；說明見檢測報告第 6 節）。
- [ ] 外部監控（UptimeRobot）仍在運作、通知信箱正確。
- [ ] 系統管理員 S／A 的雙重驗證手機都還能用；人員異動時更新管理員名單。
- [ ] 套件弱點：在專案資料夾執行 `npm audit`，有高風險項目再升級。
- [ ] Vercel → Logs 搜尋 `[csp]`，確認沒有新的誤報後，把內容安全政策從「只記錄」改成「強制」（見檢測報告第二級第 7 項）。

## 8. 已知限制（如實說明）

- 免費方案沒有資料庫自動備份與時間點還原（PITR），這套系統自己的每日備份是唯一的保險；備份最多可能漏掉最近一天的資料。
- 完整的「還原到另一個全新資料庫」演練目前做不到（備份不含登入帳號），只能做第 5 節的驗證與抽樣比對。若學校將來升級付費方案，Supabase 會提供自己的備份與時間點還原，屆時應再做一次完整演練。
- 告警目前依賴每日一次的檢查加上外部監控；沒有即時的慢查詢、錯誤率、登入被限流（429）告警。這些需要 Vercel／Supabase 付費方案的記錄匯出功能。
- 慢查詢清單來自資料庫的累計統計（用 `pg_stat_statements`），平均值會受過去資料影響；本次建立監控時已把統計歸零，之後的數字反映的是修正後的狀況。

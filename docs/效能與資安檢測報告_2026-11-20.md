# 校務行政系統：效能／極限測試與資安檢測報告

檢測日期：2026-11-20（週五傍晚，非上課時間）　檢測對象：正式站（Vercel `school` ＋ Supabase「校務行政」首爾區）

---

## 0. 先看結論

| 問題 | 結論 |
|---|---|
| 100 位教師**同時瀏覽、查詢** | **勉強可以**，平均回應約 3 秒，偶有逾時 |
| 100 位導師**在同一節上課時間點名並儲存** | **目前不行。** 預估資料庫要花 **4～9 分鐘**才處理完，期間大量查詢會被系統砍掉（8 秒逾時）。就算只有現在的 41 位教職員，同時點名也會拖到 2～4 分鐘 |
| 目前安全承載 | 約 **每分鐘 12～24 位導師**完成一次「開頁→點名→儲存」。上課鐘響後全校導師集中在 3～5 分鐘內點名，會接近上限 |
| 瓶頸在哪 | 不在網站伺服器（Vercel 會自動擴充），而在**資料庫的權限政策與「逐位學生各查一次」的寫法** |
| 修正後預期 | 做完第 1～3 項（見第 5 節），承載可提升 **5～10 倍**，100 人同時點名可壓到約 30～60 秒內處理完 |
| 資安整體 | 基礎紮實（權限政策、金鑰分層、稽核、速率限制都有），但有 **1 個嚴重等級的套件弱點（Next.js）**、**未登入者可讀到教師名單**、**缺安全標頭**，建議一個月內處理 |

> **重要說明（請先讀）**：本報告的「100 人」數字是**實測單一使用者耗時＋正式站歷史統計＋排隊模型推算**，不是 100 條真實連線的實測。原因與補測方法見第 6 節。

## 2. 效能測試結果

### 2.1 方法
1. 從資料庫的查詢統計（`pg_stat_statements`）取得**真實使用者**累計的耗時排行（數萬次呼叫）。
2. 在資料庫內以**真實導師的身分與權限**（模擬 JWT，完整經過權限政策）重跑網頁會發出的查詢，量測每一步耗時。全程唯讀；寫入測試在交易內執行後回滾，已驗證資料庫沒有留下任何資料。
3. 以量到的耗時建立承載模型，推算 41／100 位教師的情況。

### 2.2 正式站累計統計（真實使用者）

| 查詢 | 呼叫次數 | 平均 | 最慢 | 累計耗時 |
|---|---:|---:|---:|---:|
| **缺課統計檢視表 `student_absence_counts`（每位學生各查一次）** | **37,520** | 286 ms | 3.8 s | **10,717 s（約佔 65%）** |
| 出缺勤區間查詢（導師點名頁） | 937 | **3,320 ms** | 8.0 s | 3,111 s |
| 儲存點名（批次寫入） | 1,290 | 565 ms | 4.9 s | 728 s |
| 選課名單（含學生、班級） | 164 | **2,568 ms** | 7.4 s | 421 s |
| 通知輪詢（每個分頁每 60 秒一次） | 30,683 | 12 ms | 0.8 s | 372 s |

### 2.3 單一導師實測（資料庫閒置、5 次重複）

| 步驟 | 耗時 |
|---|---:|
| 取得身分 `my_effective_identity` | 7～38 ms |
| 導師班名單（約 42 人） | 58～83 ms |
| 近一週出缺勤（約 42 人） | **894～1,326 ms** |
| 單一學生缺課統計 | 69～126 ms |
| **開啟點名頁合計** | **1.44～1.76 s（平均 1.61 s）** |
| 儲存整班點名（30～42 列，已回滾） | 378～559 ms（約 12 ms／列） |
| 整學期出缺勤（單班） | 4.4 s |
| 「全部在籍選課」（管理類頁面） | **6.6 s**（已接近 8 秒逾時） |

> 只讀「一班一週」約幾百列資料就要 1 秒以上，代表問題不在資料量，而在**每一列都要跑權限函式**。另外實測也出現過一次：導師身分查整張出缺勤表直接觸發逾時。

### 2.4 根本原因（已用程式與資料庫定義確認）

1. **出缺勤表的讀取權限政策逐列執行函式**：`attendance_read` 對每一列呼叫 `can_read_attendance()`（內含 2 個 EXISTS 子查詢）；另有 `student_is_hidden()`、`is_linked_parent()` 等政策，多條政策以 OR 串接，每列都要全部評估。這與 sql/157 修好 `students` 之前的問題完全相同（當時 19 秒→1.7 秒），但 **attendance、enrollments、scores 還沒套用**。
2. **點名儲存後，對「每一位被異動的學生」各發一次缺課統計查詢**（[weekly/page.tsx:903](app/(app)/attendance/weekly/page.tsx:903)、[mobile/page.tsx:541](app/(app)/attendance/mobile/page.tsx:541)）。正式站統計是**每次儲存平均 29 次**額外查詢，總耗時是儲存本身的約 15 倍。
3. **Vercel（美東）與 Supabase（首爾）跨洋**：`getCaller()` 每個 API 要依序做 4 次往返（驗證 token、查 app_users、查角色委派、查部門），每次約 200 ms 往返，光驗證身分就近 1 秒。
4. Supabase 效能檢查：**356 處「同一表多條寬鬆政策」**、104 個外鍵沒有索引、13 個沒用到的索引。

### 2.5 100 位教師承載推算

假設：2 vCPU、查詢以 CPU 為主、DB 時間可線性疊加。單次「點名循環」DB 時間＝開頁 1.6 s ＋ 儲存 0.57 s ＋ 缺課統計 29 次 × 0.1～0.286 s ≈ **5～10.5 s**。

| 情境 | 負載 | 預估結果 |
|---|---|---|
| A 一般使用：100 人，每人約每 2 分鐘動作一次（只開頁、查詢） | 約 1.3 核秒／秒＝約 67% 使用率 | 平均約 3 秒，尖峰可能超過 8 秒逾時 |
| **B 上課鐘響後 1 分鐘內 100 人同時點名並儲存** | 約 500～1,050 核秒 ÷ 2 | **需要 4～9 分鐘才清空**；排隊中的查詢超過 8 秒被砍，使用者會看到失敗或轉圈 |
| B′ 同上但只有現在的 41 人 | 約 205～430 核秒 ÷ 2 | 2～4 分鐘（與正式站平均 3.3 秒、最長 8 秒的實際紀錄吻合） |
| C 修正第 1～3 項之後的 B（預估） | 每循環降至約 0.65 s | 100 人約 30～60 秒內處理完 |
| 其他限制 | 資料庫連線上限 60（已用 16）；校內同一個對外 IP 的登入速率限制（見第 3 節 M5） | 早上 100 人同時登入可能先被擋在登入端 |

## 3. 資安檢測結果

### 3.1 已確認做得好的部分
- **未登入者讀不到敏感資料**：用公開的 anon 金鑰逐表試探，`students`、`attendance`、`scores`、`enrollments`、`staff_notifications`、`rate_limits`、`feature_usage`、`student_absence_counts` 皆回 401；`app_users`、`clock_records`、`change_audit_log`、`site_content` 回 0 列；`/storage` 無公開儲存桶。
- **金鑰分層正確**：service role 只在伺服器端；`.env.local` 已被 `.gitignore`；掃描追蹤檔案與整份 git 歷史，**沒有任何 JWT／資料庫密碼／sb_secret 外洩**。
- **所有 API 路由都有身分驗證**（`getCaller`、`requireOrganizer`、`requireDevOrSystemAdmin`、`CRON_SECRET`）；排程用密鑰驗證；公開競賽頁走 32 位元組隨機 token。
- 112 個 SECURITY DEFINER 函式已收回未登入執行權；家長入口有登入／註冊速率限制；改密碼有外洩密碼比對（HIBP k-anonymity）；預設弱密碼強制更換。
- 有稽核紀錄（出缺勤與全表異動）、每日備份排程、開發人員唯讀角色、CI（型別、測試、建置）。
- 體驗版（Demo）帳號與固定密碼受環境變數閘控，正式資料庫確認**沒有**任何 `demo-*@example.com` 帳號。

### 3.2 發現的問題

| 編號 | 等級 | 問題 | 說明 |
|---|---|---|---|
| H1 | **高** | **Next.js 14.2.35 有已知弱點** | `npm audit`：4 項（1 嚴重、1 高、2 中）。Next.js 有 11 則公告（快取混淆、SSRF、Server Function 暴露、DoS 等）；postcss（高）、uuid（中，經 exceljs）。本專案未使用 `next/image` 與 Server Actions，其中影像最佳化 RCE 與 Server Actions 類**不直接適用**，但仍應升級；修補需升主版本（15／16） |
| M1 | 中 | **未登入者可讀取教師名單與班級表** | `teachers` 與 `classes` 的 `read_*` 政策為 `true`（含 anon）：任何人拿到網站公開金鑰即可取得 **41 位教職員姓名、其登入帳號 UUID（app_user_id）、34 班導師對應**。登入頁並未使用這兩張表 |
| M2 | 中 | **缺安全標頭** | `next.config.mjs` 沒有 CSP、X-Frame-Options（防點擊劫持）、nosniff、Referrer-Policy、Permissions-Policy；也沒有 middleware，各頁面自行檢查登入 |
| M3 | 中 | **教職員登入沒有應用層防暴力猜測／驗證碼** | 教職員直接呼叫 Supabase 登入（[app/page.tsx:213](app/page.tsx:213)）；只有家長入口有鎖定。密碼最短 6 碼；弱密碼清單只有 2 組；管理員（S／A）未啟用 MFA |
| M4 | 中 | **預設密碼流通風險** | 程式碼內寫死兩組已公開流傳的預設密碼（用於強制改密碼）。代表帳號開通時仍使用共用預設密碼，在改密碼前是弱點窗口 |
| M5 | 中 | **全校共用同一個對外 IP 的登入速率限制** | Supabase 登入／換發 token 依 IP 限速（官方文件：token 換發 1,800 次／小時、突發 30；驗證 360 次／小時）。100 位教師同時登入，可能互相擋住。請到後台 Authentication → Rate Limits 確認並調整 |
| L1 | 低 | Supabase 檢查：20 個函式 search_path 可變；103 個 SECURITY DEFINER 函式登入者可執行（多為權限政策輔助函式，屬設計） | 已在 sql/156 處理一批；剩下的建議逐一確認，非 SECURITY DEFINER 的一般 SQL 函式刻意不加（避免變慢） |
| L2 | 低 | 外洩密碼保護（Supabase 內建）未啟用 | 免費方案不提供；已用自建 HIBP 檢查補上，僅涵蓋「自己改密碼」與「忘記密碼」兩條路徑，管理員重設密碼（reset-password）與新增帳號未涵蓋 |
| L3 | 低 | Vercel 對 `*.vercel.app` 啟用 SSO 保護 | 目前網址需 Vercel 帳號才能開啟；正式讓教師使用前需綁**自訂網域**（保護不涵蓋自訂網域）或調整設定。也使外部壓力測試無法直接打到網頁層 |
| L4 | 低 | 備份與可用性 | 免費方案無每日備份下載、無時間點還原（PITR）、7 天無活動可能被暫停；雖有每日備份排程，建議定期做還原演練 |
| L5 | 低 | 個資管理 | 約 1,346 位學生個資存放於海外區域（首爾）。建議確認是否符合教育主管機關與個資法對委外／跨境處理的要求，並保留告知與契約文件 |

## 4. SWOT 分析（資安＋效能）

### S 優勢
- 資料庫層權限政策（RLS）完整，未登入者讀不到學生、成績、出缺勤。
- 金鑰管理正確，git 歷史無外洩；API 皆有驗證，排程有密鑰。
- 工程體質：CI（型別／測試／建置）、型別檢查不再略過、稽核紀錄、每日備份、開發人員唯讀角色。
- 已有成功的效能優化範例（sql/157：19 s → 1.7 s），**修法已驗證可行且可複製**到其他表。
- Vercel 無伺服器架構可自動擴充；目前資料量小（58 MB），調校空間大。

### W 劣勢
- 出缺勤／選課／成績表的權限政策仍逐列執行函式；單班一週查詢就要 1 秒以上。
- 點名儲存後「每位學生各查一次」的 N+1 寫法，占資料庫總耗時約 65%。
- Vercel 在美東、資料庫在首爾；身分驗證每次 4 次序列往返。
- 運算資源小（約 Micro、連線數 60）。
- Next.js 版本過舊、未設安全標頭、教職員登入無應用層防護、密碼規則偏弱。
- 目前沒有可重複執行的壓力測試與監控（這次才補上腳本）。

### O 機會
- 套用 sql/157 同樣模式即可得到 5～10 倍改善，不需改使用者流程。
- 把 Vercel 區域改為 icn1（首爾）、合併驗證查詢，可立即減少約 0.5～1 秒／API。
- 升級付費方案後可加大運算規格、取得每日備份、PITR、不會閒置暫停。
- 以 Supabase Realtime 取代 60 秒輪詢；啟用 MFA、Turnstile 驗證碼，補強帳號安全。
- 已有 `queryCache` 與快取層，可擴大套用在不常變動的資料（學期、班級、節次）。

### T 威脅
- **開學日／鐘響後全校同時點名**：目前架構會排隊並大量逾時。
- 共用校內 IP 造成登入速率限制互相影響。
- Next.js 已知弱點被利用；教職員帳號被撞庫（共用預設密碼 ＋ 無驗證碼）。
- 教師名單公開可讀，可被用於釣魚或針對性猜密碼。
- 免費方案的暫停／無備份風險；資料庫單點故障。
- 個資法規與跨境儲存的合規風險。
